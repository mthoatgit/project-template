## Core

Every `/new-project` run vendors a frozen snapshot of `skeleton/orchestrator/` into the new downstream project. Improvements and fixes made afterward never reach projects that already scaffolded — there is no update path, only drift. The idea: pull the orchestrator out into its own repository, developed through the same backlog/stage workflow project-template uses on itself. The concrete consumption mechanism (how downstream projects reference it instead of copying it — package dependency, subtree, or something else) is an open question for Stage 3 (Architecture), not decided here. A further consideration raised during capture: whatever mechanism is chosen should eventually also allow the orchestrator to be used as an importable library, not just a CLI entry point.

Item entered Stage 1. Trigger was a backlog review at session start: items 001..034 are archived, leaving this item as the only active one in `project-template`.

**The user's framing of the target state.** Asked to confirm the goal, the user specified the shape rather than just restating it — *"die idee ist eher das der orchestrator nicht mehr im skeleton vorkommt und auch nicht in den downstream projekten sondern als eigenes repo hingelegt bzw. gecloned wird und dann eben alle projekte diesen orchestrator benutzen. wir müssen nur sicherstellen, dass das projekttemplate das klonen des projekts sicherstellt und das die downstream projekte diesen orchestrator benutzen nur eben nicht aus dem skeleton"*. Three commitments are in that sentence: the orchestrator disappears from `skeleton/` entirely; no copy lands in downstream projects at all; and there is **one** cloned instance that every project uses, with `project-template` responsible for ensuring that clone exists. This is a shared-installation model, not a per-project dependency model — closer to how `~/.claude/skills/` is shared across every project on this machine from the `dotfiles-claude` repo than to a vendored or per-project-installed package.

**Discovered state — the counterpart work already exists and is ahead of this item.** `~/dev/orchestrator` is a real repository, scaffolded from `project-template`, carrying its own `docs/concept.md`, its own backlog, and item `001-orchestrator-own-home` ("Give the orchestrator loop its own home and a real specification base"). That item has Stage 1 (Concept) and Stage 2 (Requirements + Epic-Birth) both approved: Epic `E1-foundation` was born with `REQ-0001` (runtime code home), `REQ-0002` (test suite passes), `REQ-0003` (downstream consumption path). Its Stage 3 (Architecture) is not yet opened, and `REQ-0003` carries `Architecture-impact: pending (see Stage 3)`. So the governance question — whether the extracted orchestrator is a project in its own right with its own concept, backlog, and lifecycle — is already settled in the affirmative by facts on disk, not open for this item to decide.

**The division of labour is already written down, on the other side.** `REQ-0003` states that downstream projects must be able to obtain the loop in a form that admits updates, leaves the mechanism to Stage 3, and names "the counterpart change tracked in `project-template`'s own backlog (item 035)" as the half that switches downstream scaffolding away from copying. The orchestrator repo's concept reinforces this from the other direction, listing under Scope → Out: "Changes to how downstream projects are scaffolded by `project-template`. The counterpart question — how downstream projects switch from copying to consuming — lives in `project-template`'s own backlog and is not resolved here." This item therefore has a sharper scope than its day-zero framing suggests. It does **not** own moving the code — that is `REQ-0001` over there, and the user's widening of scope to include `orchestrator-tests/` is likewise the other repo's Stage 3/4 business. What this item owns is the `project-template` side: removing `skeleton/orchestrator/` from the scaffold, ensuring the shared clone exists, and making scaffolded projects resolve the orchestrator externally.

**Two questions the day-zero framing raised are already answered elsewhere and are not live here.** Whether `docs/orchestrator-requirements.md` moves as-is or gets re-expressed as REQs: the orchestrator's concept declares that file reverse-extracted from the code and drifted, names the test suite as the truest specification the loop has, and puts reverse-engineering REQs from the tests explicitly out of scope as its own future work. And the capture note's "importable library, not just a CLI entry point" is a property of the package layout, which is `REQ-0001` plus that repo's Stage 3 — it constrains this item only insofar as whatever consumption path is chosen must not foreclose it.

**What is left for this item's Stage 1 to actually decide: what `project-template` becomes.** Today the project defines itself partly through owning the loop — `CLAUDE.md` names `skeleton/orchestrator/` "the canonical orchestrator source", lists 164 orchestrator tests under `## Verification`, and documents `pytest` as the project's test command. `skeleton/orchestrator/` is 13 modules / 2331 LOC and `orchestrator-tests/` a further 10 modules / 2254 LOC — roughly 4.6k of the ~4.6k LOC this repo owns. Once that leaves, `project-template` is a pure scaffold-and-workflow supplier that references an external execution engine and has no runtime code and no test suite of its own. That is a genuine change to what the project *is*, which points at Stage 1 producing an artefact rather than a null. Complicating factor: `docs/concept.md` does not exist for `project-template` at all — items 001..034 were retro-documented without ever producing one, and the root `docs/` holds only `backlog/` and `orchestrator-requirements.md`. So the Stage 1 artefact here would be an initial write describing the whole project post-extraction, not a delta amendment.

**Sequencing risk — the mechanism must be decided once, not twice.** The consumption mechanism is jointly owned: `REQ-0003`'s Stage 3 in the orchestrator repo, and this item's Stage 3 here. Two independent Stage 3 discussions on the same question is exactly how the two halves drift apart. The natural ordering is that the orchestrator repo's Stage 3 decides the mechanism, since it owns `REQ-0003` and the package-layout constraint that shapes it, and this item's Stage 3 consumes that decision and works out the scaffolding consequences. Recording this here so this item's Stage 3 does not re-open a settled question.

**Cost of the single-shared-clone model, recorded now so Stage 3 inherits it.** One clone used by every project is the maximal answer to the drift problem in the Core — no project can ever be stale, because there is only one installation. The inverse is that no project can pin either: a change landed in the orchestrator repo reaches every project on the machine at once, including a breaking one, with no per-project opt-out and no version boundary to roll back to. `REQ-0003` is written more loosely than this ("a form that admits updates") and would also be satisfied by a pinned-and-upgradable mechanism. Whether the always-latest property is wanted or merely accepted is an intent question. [NEEDS CLARIFICATION → Stage 3: is "every project always runs the current orchestrator, no pinning" the desired property, or should the mechanism allow a project to pin a version and upgrade deliberately?]

**Scope boundary not yet drawn: existing projects.** The Core frames the pain as projects that already scaffolded being stuck with a frozen snapshot. `~/dev` currently holds several such projects. Whether this item covers de-vendoring them — removing their copied `orchestrator/` and pointing them at the shared clone — or only changes what *new* projects get, is a scope decision that belongs to this stage. [NEEDS CLARIFICATION: does this item cover retrofitting already-scaffolded downstream projects, or only the forward path for newly scaffolded ones?] — **resolved below, same day: in scope, all six.**

**The sequencing risk resolved itself in the right order.** Later the same day, `~/dev/orchestrator`'s item `001-orchestrator-own-home` ran all five stages and archived. Epic `E1-foundation` is implemented and merged to `main`; 173 tests pass. Three ADRs now bind this item: `ADR-0001` (tech stack — Python 3.11+, stdlib-only runtime, pytest as a dev dependency, PEP 621 + setuptools, `src/` layout, console script *and* `python -m`), `ADR-0002` (package layout and self-hosting — the `Edit(orchestrator/**)` deny rule removed rather than dodged, so the loop's repository can drive itself), and `ADR-0003` (shared installation). The consumption contract is written down at `~/dev/orchestrator/docs/consuming-the-orchestrator.md`, whose closing section names item 035 as the owner of the setup side. The mechanism was therefore decided once, over there, exactly as the note above asked — this item consumes it and does not re-open it.

**Marker resolved — pinning. Case A, closed by `ADR-0003`.** The mechanism is an editable install (`pip install -e`) from one shared clone. `ADR-0003` does not merely permit always-latest, it forbids offering the alternative: *"Per-project version pinning MUST NOT be offered as a property of this system"*, and it records always-latest as *"an accepted intent, not a tolerated side effect — this ADR is the place that says so, so a future item proposing pinning is proposing a reversal rather than an addition."* Two rejected candidates are on record there as well: a shared clone on `PYTHONPATH` (global invisible state) and a launcher shim on `PATH` (serves the CLI only, forecloses library use). The open question this item recorded is answered, not deferred to its own Stage 3.

**The mechanism was demonstrated, not only specified.** `~/dev/orchestrator`'s `TEST-0006` records a consumer built by following the documented obtain step: its `site-packages` held no orchestrator code at all, only a `.pth` file pointing at `.../orchestrator/src`. A change made in the orchestrator repository was visible to that consumer on its next invocation with nothing touched on the consumer side, and reverting it propagated the same way. The always-latest property is observed behaviour here, not a claim inherited from the design.

**No remote is not a gap.** `ADR-0003` requires the clone to be *available at a known location*, not to be clonable from a server. `~/dev/orchestrator` has no remote and satisfies the ADR completely — on the machine where the loop is developed the shared clone and the development tree are the same directory, so a change is live the moment it exists on disk and committing does not make it travel. A remote would matter only for a second machine or for backup, neither of which is being asked for. Recorded because the absence looks like an omission and is not one.

**Delete authorisation, verified here rather than taken on trust.** Comparing `skeleton/orchestrator/*.py` against `~/dev/orchestrator/src/orchestrator/` file by file: 12 of 14 modules are byte-identical, and `claude.py` differs. Likewise 11 of 12 test modules match and `test_claude.py` differs. Both divergences run the same direction — the orchestrator repository is strictly *ahead*, carrying `ADR-0002`'s removal of the self-edit deny rule and the docstring that used to promise a protection the deny list never actually gave. Nothing in the skeleton copy is unique to it, so `skeleton/orchestrator/`, `orchestrator-tests/`, and `pytest.ini` can be removed with nothing to preserve. Worth recording that the drift the Core predicts is already observable elsewhere: `orchestrator-dashboard` carries 12 modules where the other vendored projects carry 14.

**The visibility half is the real work, and it is smaller than it first looks.** These are two unequal problems, not one. *Availability* is a once-per-machine fact — the clone exists and `pip install -e` has run — and it is not a per-project concern at all. *Reference* recurs at every scaffold and is the substantive half. Technically a downstream project needs nothing: the editable install puts the `orchestrator` console script on `PATH` and makes `python -m orchestrator` resolve from any working directory, so `orchestrator --tasks docs/tasks/ --project-dir .` runs in a project that contains no trace of the loop. What de-vendoring removes is therefore not capability but *evidence*. Today one trips over an `orchestrator/` directory; afterwards nothing in the project would mention the loop, and a session landing in `dice-roller` would have no way to learn that an execution engine exists. The mitigation is already half-built: `skeleton/CLAUDE.md` carries an `## Implementation` section that names the loop, so the fix is a rewording of that section — the correct invocation form plus a statement that the code is installed and lives in `~/dev/orchestrator` — rather than a new section to invent.

**Marker resolved — existing projects. Decision: in scope, all six.** Five downstream repositories hold a vendored copy (`dice-roller`, `kitchen-inventory`, `orchestrator-dashboard`, `palette-picker`, `wordfreq`), and `project-template` itself is the sixth. The user's Stage 1 framing already reached for this — *"nicht mehr im skeleton ... und auch nicht in den downstream projekten"* — and the per-repository work is mechanical: delete `orchestrator/`, correct the two `## Implementation` lines in `CLAUDE.md`. `orchestrator-dashboard` needs slightly more care, carrying an older `orchestrator/tests/` layout plus its own `pytest.ini`, and being a consumer of the loop's *output* as well as its code. The objection that this item's artefacts cannot verify state in other repositories does not hold: the procedural TEST mode exists for exactly this kind of cross-repository check.

**New surface, not previously recorded — the workflow instructions live in a third repository. Decision: in scope.** `~/.claude` is the separate `dotfiles-claude` repository, and ten of its files mention the orchestrator. Almost all survive the extraction untouched, including `/scaffold`, whose `python -m orchestrator` keeps resolving from `site-packages` regardless of working directory. **The orphaned requirements document, audited rather than assumed.** `docs/orchestrator-requirements.md` at this repository's root lists `REQ-01`..`REQ-42` and describes the loop, so the extraction leaves it with no subject here. ## Stage 2 — Requirements + Epic-Birth

### Discussion

#### 2026-08-15

**Epic-birth, because there is nothing to join.** Root `docs/specs/` did not exist — items 001..034 were retro-documented without ever producing a requirement — so this stage creates the requirements tree, the first Epic, and starts the `REQ-NNNN` counter at `0001`. `E1-orchestrator-extraction` is therefore this project's founding Epic in fact as well as in numbering.

**The decomposition, and why it is six rather than four.** Stage 1's scope produced six behaviours that stand independently: the scaffold stops shipping the loop (`REQ-0001`), a scaffolded project says how its tasks get executed and where the engine lives (`REQ-0002`), `/new-project` reports a missing shared installation (`REQ-0003`), this repository stops retaining loop source, tests, build config, and the legacy requirements document (`REQ-0004`), the five already-vendored projects are de-vendored (`REQ-0005`), and the two dead passages in the workflow commands go (`REQ-0006`).

Two pairs look mergeable and are not. `REQ-0001` and `REQ-0004` are both deletions, but the first governs what downstream *inherits* and the second what this repository *keeps*; the scaffold can be clean while the root still holds a test suite for code that lives elsewhere, so satisfying one says nothing about the other. `REQ-0003` and `REQ-0006` both land in `dotfiles-claude` and both touch `/new-project`, but one adds a check and the other removes dead text, with nothing shared in their acceptance.

**Structural problem: half this Epic cannot be in its own pull request.** `workflow-epics` binds an Epic to one branch and one PR, and that model assumes a single repository. `REQ-0005` delivers into five separate project repositories and `REQ-0003`/`REQ-0006` into `dotfiles-claude`, so three of six requirements describe commits no PR of this Epic can contain. Three shapes were weighed: one Epic with those three carried as procedural work; a split into `E1` (here) and `E2` (elsewhere); and keeping only the local three here while filing items in each target repository. The split was rejected because `E2` would have inherited the identical problem — it moves the boundary rather than resolving it. Per-repo items were rejected as the most bookkeeping for the least gain, and because `dotfiles-claude` has no backlog to file into. **Decision: one Epic, with the cross-repository requirements carried as procedural work items and verified by procedural TEST specs at Stage 5** — the mode `workflow-tests` already defines for verification that is not a code assertion. The Epic's PR carries this repository's diff; the procedural specs carry the proof that the rest happened.

**Architecture-impact assignments.** Five of the six are `none (no ADR)`: the consumption mechanism was already decided by the orchestrator's `ADR-0003`, and deletions plus documentation wording force no architectural decision here. `REQ-0003` is left `pending (see Stage 3)` — where the availability check lives, what it examines, and how it behaves when the installation is absent are genuine design questions rather than settled ones.

**Note for Stage 3, recorded now.** Root `docs/adr/` does not exist, so the founding-ADR rule in `workflow-lifecycle-featurework` applies: Stage 3 MUST produce `ADR-0001` (tech stack) regardless of what the REQs demand, and is not allowed to null-decide while the directory is empty. Post-extraction that ADR describes a project with no runtime, which is unusual but not empty — files only, Markdown as the medium, no build step, and a deliberate dependency on two repositories it does not version.

## Stage 3 — Architecture

### Discussion

#### 2026-08-15

**The founding ADR lands here by accident of history, and the timing helps.** Root `docs/adr/` was empty, so the founding-ADR rule fires and this stage may not null-decide. It falls to item 035 rather than to an item 001 because items 001..034 were retro-documented without ever running the lifecycle. Had a tech-stack ADR been written before this item, it would have recorded Python 3.11+, a stdlib-only runtime, and a 164-test pytest suite — every part of which is leaving under `REQ-0004`, and all of which belongs to the orchestrator. Writing it now describes what remains rather than what is departing.

**What a tech-stack ADR says about a project with no code.** Markdown, a directory shape, configuration copied verbatim; no language, no runtime, no build step, nothing to execute. The absence is the commitment — stated so that tooling with no user does not slowly accrete. The harder half is the dependency stance. `docs/concept.md` records under Constraints that three repositories must stay in agreement and none is versioned with the others, but a line in a prose document reads as an observation, and this is a position: the orchestrator's `ADR-0003` chose one shared installation over pinning and narrowed this project's role to ensuring availability. Recording it as architecture is what makes a future proposal to vendor, pin, or sub-module either sibling legible as a reversal rather than an improvement. Splitting stack and dependency into two ADRs was considered and rejected as artificial — for a project with no code, what it is made of and what it leans on are one subject, and a stack ADR omitting the two repositories would describe something that cannot do anything.

**`REQ-0003` was the only REQ carrying `pending`, and it resolves to an ADR.** The candidates for what the availability check inspects were the clone directory at a known path, the console script resolving, or both in order to discriminate the two failure causes. The directory check was rejected outright: it passes on a machine where the clone was never installed, which is the more likely failure, so it would report success on a broken setup. The discriminating variant was rejected on the minimalism rule — the case it uniquely catches, "cloned but not installed", is already served by one check whose failure message names both causes, and a second probe buys a diagnosis the user can reach from the message anyway. **Decision: check that the `orchestrator` console script resolves**, the exact surface `consuming-the-orchestrator.md` tells users to invoke, which proves clone and installation together.

**What makes that ADR-worthy is not the command but the stance beneath it.** This repository is asserting another repository's install contract, and accepting a known blind spot while doing so. The orchestrator's `ADR-0003` names it among its own negatives: the editable install is per Python environment, so a project with its own virtualenv needs the install repeated there, and nothing inside that project records the requirement. A check run from `/new-project`'s shell therefore passes while the project's own environment lacks the package. Unwritten, the next person to hit that case fixes it by recording install state per project — which is vendoring in a different coat, and a reversal of the decision this whole item exists to implement. Written down, it is a known limit with a stated reason.

**The other five REQs confirm as `none`.** `REQ-0001`, `REQ-0004` and `REQ-0005` are deletions; `REQ-0002` and `REQ-0006` are documentation wording. None forces a technology choice, a boundary rule, or a dependency stance that `ADR-0001` does not already cover, and the consumption mechanism itself was decided in the orchestrator's `ADR-0003` rather than here.

**`system-design.md` written alongside `ADR-0001`, not deferred.** The architectural picture is not going to get clearer than it is now, and the one thing a newcomer must understand before touching anything — the line between `skeleton/` and the root, and which side a given file is on — had no home in any document. It rides `ADR-0001`'s commit per the coupling rule in `workflow-architecture`.

### Outcome

`ADR-0001` in `docs/adr/0001-tech-stack.md` (founding — files only, and a standing dependency on `~/dev/orchestrator` and `dotfiles-claude`), with `docs/architecture/system-design.md` written in the same commit. `ADR-0002` in `docs/adr/0002-availability-check.md` grounding `REQ-0003`, whose `Architecture-impact` is back-filled from `pending` in that ADR's commit. `REQ-0001`, `REQ-0002`, `REQ-0004`, `REQ-0005` and `REQ-0006` confirmed as `none (no ADR)`.

**Approved:** 2026-08-15
